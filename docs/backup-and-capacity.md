# Периоды, резервное копирование и проверка объёма данных

## Учёт оказанных услуг

Решение пользователя от 17.10.2026: закрывать периоды вручную, разрешать отмену, сохранить уже показанное историческое использование. Расходы оплачивают исполнителей и не закрывают периоды услуги.

`service_usage` хранит уникальную пару `(invoice_id, period)`, состояние закрытия, источник, время и автора последнего изменения. Миграция 0005 создаёт строки 1…`periods_used` с источником `legacy`, без выдуманной даты закрытия. Число в счёте сохраняется. `periods_used` становится производной проекцией журнала. Пересчёт при старте по расходам удалён.

`POST /api/invoices/:id/periods` принимает `{period: N, closed: true|false}`. Закрывается следующий период, отменяется последний закрытый. Сервер блокирует счёт, проверяет роль и текущий номер, затем в одной транзакции меняет журнал, пересчитывает баланс, пишет аудит, outbox и квитанцию идемпотентности. Повтор с тем же ключом возвращает исходный результат; повтор с новым ключом и устаревшим номером получает 409. Расходы по подписке больше не создают ложное уведомление о закрытии периода.

Admin/assistant/accountant работают в существующих границах видимости. Client/partner не меняют использование. Смена единицы и преобразование в разовый счёт с закрытыми периодами запрещены. Общее количество нельзя уменьшить ниже использованного. Историческое закрытие также можно отменить; это явное изменение с аудитом.

После первого ручного изменения нельзя запускать версию до этой миграции: её startup-пересчёт снова выведет использование из расходов. Скрипт активации блокирует такой автоматический откат. В этой ситуации нужен выпуск исправленной версии или осознанное восстановление защищённой копии перед переключением.

## Формат резервной копии

Новые файлы `.fdb` содержат заголовок `fdb1/schema=5`, gzip-поток записей и AES-256-GCM с аутентификацией заголовка. Ключ выводится из существующего `ACCESS_CODE_SECRET` с отдельной меткой формата; в production отсутствие секрета запрещает создание копии. Секрет не входит в архив и должен храниться отдельно.

Все 22 таблицы читаются в одной `REPEATABLE READ READ ONLY` транзакции через SQL-курсоры. Получение данных ограничено 250 строками; для документов — 1 строкой. Поток учитывает обратное давление. Документы включаются вместе со ссылками и SHA-256. PostgreSQL timestamps сохраняют микросекунды; преобразование через JS Date при восстановлении не обрезает точность. Файл публикуется атомарно после завершения потока. Список копий читает только файловые метаданные. HTTP-скачивание отдаёт зашифрованный файл потоком.

Ручное создание возвращает 202 и записывает задание в `scheduled_jobs`. Worker продолжает работу при закрытии страницы. Интерфейс отдельно показывает постановку в очередь, выполнение, ошибку/повтор и готовый файл. Ежедневная копия выполняется в 03:00 UTC / 06:00 МСК, сохраняются последние 30 автоматических копий.

Перед восстановлением полностью проверяются аутентификация, схемы строк, порядок и наличие каждой таблицы, количество строк и хеши документов. Затем создаётся текущая резервная копия. SQL заменяется одной транзакцией, вставки ограничены 250 строками или 1 MiB. Сессии отзываются. Сбой после удаления/вставки откатывает всю SQL-транзакцию. Неизменяемые файлы публикуются до коммита ссылок; лишние объекты при неудаче не делают ссылки битыми.

JSON 2/3/4 остаётся читаемым, исторические периоды восстанавливаются из сохранённого счётчика. Старый формат ограничен 64 MiB; новые большие копии используют `.fdb`. Лимит одной записи архива — 20 MiB; лимит загружаемого документа приложения — 10 MiB. Потребление памяти ограничено порциями и размером одного документа, но свободный диск всё равно должен вместить архив, защитную копию, данные PostgreSQL и WAL. Хранение файла только на том же сервере не заменяет отдельную внешнюю копию.

Для большой копии используйте режим обслуживания без HTTP-таймаута:

```sh
# На сервере, файл доступен пользователю financeduck; секрет берётся из .env.
cd /opt/finance-duck
sudo -u financeduck node --env-file=.env dist-server/backupCli.js verify /var/finance-duck/backups/backup-manual-....fdb
sudo bash deploy/restore-backup.sh /var/finance-duck/backups/backup-manual-....fdb
```

Скрипт сначала проверяет файл, затем останавливает web/worker, выполняет восстановление, снимает аренды остановленных заданий и снова запускает сервисы. После завершения проверяется health. Во время восстановления доступ к приложению закрыт; восстановление старого снимка намеренно возвращает данные к его времени. Активные сессии нужно открыть заново. Доставка уведомлений остаётся at least once; восстановление исторического outbox требует учитывать возможные повторные уведомления.

## Воспроизводимые измерения

```sh
TEST_POSTGRES_URL=postgres://postgres@127.0.0.1:55439/postgres npm run test:postgres
TEST_POSTGRES_URL=postgres://postgres@127.0.0.1:55439/postgres npm run test:load
```

`test:postgres` создаёт отдельную БД, проверяет конкурентные команды и полный зашифрованный round trip с PostgreSQL-типами, затем удаляет БД. `test:load` также создаёт и удаляет только собственную БД. Скрипты не используют production `DATABASE_URL` как цель. Допустим только локальный PostgreSQL. Для нагрузки используется 10 соединений приложения, V8 heap ограничен 256 MiB.

Нагрузка: 10 000/100 000 счетов, по 3 расхода на счёт, 200 клиентов, 20 партнёров. 80% запросов — страницы списка, 10% — поиск, 10% — месячная сводка. На каждом уровне 1/5/20/40 одновременных запросов — минимум 100 запросов и 10 секунд. Учёт задержки включает получение полного HTTP-ответа. Проверка авторизации измеряется отдельно регрессиями; в генераторе нагрузки авторизация фиксирована на синтетического администратора.

Заданный до финального прогона ориентир: p95 ≤ 750 ms, p99 ≤ 1500 ms, 0 ошибок. Измеряется рабочий диапазон именно этого набора запросов, а не число пользователей и не универсальный предел сервера. Отдельно выполняется копирование/восстановление всей базы со 100 документами по 1 MiB, сверка числа и отпечатков строк каждой таблицы, SHA-256 документов и проход потокового экспорта. Итоговые цифры и условия оборудования публикуются в протоколе выпуска.

Реализация курсоров следует [семантике DECLARE PostgreSQL](https://www.postgresql.org/docs/16/sql-declare.html). Бинарный PostgreSQL для локального измерения установлен только во временный каталог; зависимостей production-приложения это не добавляет.
