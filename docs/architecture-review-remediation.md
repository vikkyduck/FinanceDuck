# FinanceDuck: границы команд и выпуск исправлений ревью

## Финансовые команды

Командный сервис сам проверяет типизированные условия счёта и расходы, отбрасывает поля БД вне команды, нормализует деньги и проверяет проценты/периоды. Проверка действует и при вызове без HTTP. Повторная выдача сохранённого результата проверяет текущий доступ к счетам. Для удаления расхода/переноса ID родителей сохраняются в квитанции: повтор после удаления остаётся идемпотентным, но не обходит смену доступа.

Браузер повторяет финансовую команду 1 раз после сетевого обрыва с тем же ключом и телом. При смене сессии, отмене запроса и для других изменяющих endpoints автоматического повтора нет. Пока результат неизвестен, ручная повторная отправка того же содержимого в открытой сессии сохраняет ключ. После подтверждённого ответа следующая отправка считается новой командой. Перезагрузка вкладки очищает этот временный реестр; перед повтором после перезагрузки нужно проверить результат операции.

HTTP-маршруты счетов вызывают `InvoiceCommands`. Сервис проверяет роль и принадлежность счёта внутри транзакции, блокирует родительские строки `invoices` в порядке UUID, применяет изменение и сохраняет audit/outbox вместе с результатом. Ошибка аудита откатывает финансовое изменение. Расходы, редактирование условий и переносы используют один пересчёт из первичных данных: условия счёта, журнал расходов, переносы.

`invoices.clientBill` — исходная сумма, `invoice_calculations` — производная проекция. Для периодической услуги сумма выводится из цены и числа периодов. Переданный клиентом итог расходов не заменяет журнал. По подтверждённому решению пользователя использование учитывает отдельный журнал `service_usage`: периоды закрываются вручную, последнее закрытие отменяется. Миграция 0005 сохраняет исторический счётчик; расходы его больше не меняют. См. [правила, архив и измерения](backup-and-capacity.md).

Денежный движок использует decimal.js и округление half-up до копеек. При делении нечётной копейки вторая доля вычисляется как остаток, поэтому сумма долей равна прибыли. Изменить клиента или удалить счёт с переносами нельзя: сначала нужно отменить переносы. Ожидаемый отказ возвращает 409.

Повтор HTTP-команды с тем же `Idempotency-Key` и тем же содержимым возвращает сохранённый результат. Ключ ограничен токеном доступа. Иное содержимое с тем же ключом возвращает 409. Клиент, повторяющий запрос после сетевого сбоя, должен сохранить ключ исходной команды. Новый ключ означает новую команду.

Outbox worker забирает события с `FOR UPDATE SKIP LOCKED`, отправляет уведомления после коммита, ограничивает длительность запроса и повторяет ошибки с задержкой. Доставка имеет семантику **at least once**: сбой между отправкой Telegram и фиксацией результата может дать дубликат сообщения. При отсутствии настроенного получателя событие завершается без отправки. Реальные сообщения не являются частью автоматических тестов.

## Сессии и доступ

Изменяющие HTTP-запросы требуют сессионную cookie и непустой правильный `X-CSRF-Token`. Отсутствие заголовка возвращает 403, не уничтожая действующую сессию. Refresh/logout защищены тем же правилом. `/api/auth/validate` восстанавливает CSRF-токен для текущей сессии; чужие Origin отклоняются. Cookie использует SameSite=Lax.

Каждая сессия получает собственный QueryClient и новое дерево React. Поздний ответ предыдущей сессии остаётся в её отсоединённом кэше. `useInvoice` привязывает данные карточки к ID счёта; основной список и карточка проверяют ответы по Zod-контрактам. Роли и схемы объявлены в `shared/domainTypes.ts`.

Регулярные шаблоны всегда получают scope маршрута. Ассистент не читает, не меняет и не генерирует скрытый шаблон; бухгалтер к recurring API не допускается. Create/update принимают явный whitelist. Автор задаётся сервером; ассистент не может изменить security label. Ответ создания черновика проходит ролевую проекцию.

## Расписания и номера

Фоновые задания выполняет отдельный `finance-duck-worker.service` (`npm run worker`; локально `npm run dev:worker`). Web-процесс не запускает таймеры. В `scheduled_jobs` сохраняются статус, время следующего запуска, число попыток, последняя ошибка и результат. Атомарная аренда задания с продлением предотвращает параллельный запуск; истечение аренды позволяет продолжить после аварии. Ошибки повторяются с задержкой от 1 до 60 минут. Состояние не теряется при перезапуске.

Повторяющиеся счета и очистка лимитера проверяются ежечасно; ежедневный backup — в 03:00 UTC (06:00 МСК). Пропущенный ранее запланированный запуск выполняется после восстановления worker. Очистка `login_rate_limits` удаляет не более 5000 записей за запуск по индексу времени; активные блокировки и текущее окно попыток сохраняются.

`nextOccurrence` использует календарный якорь: 31 января → последний день февраля → 31 марта. Создание счёта, расходы, продвижение расписания, audit и outbox происходят в одной транзакции с блокировкой шаблона. Уникальный неизменяемый `recurring_occurrence_key` защищает период от дублирования; изменение даты документа не меняет его период. Старые строки без ключа проверяются по шаблону и дате. Уже существующий период тоже продвигает отставшее расписание. Для ручной генерации фиксируется текущий пользователь, для фоновой — системный источник. Ошибка аудита откатывает всю генерацию; повтор не создаёт второй audit/outbox.

Номер выдаётся атомарным счётчиком по году. Миграция заполняет его максимальным историческим номером вида `INV-YYYY-NNNN`. Удаление счёта не уменьшает счётчик.

## Резервные копии

Потоковый формат `.fdb` (схема 5) включает все 22 постоянные таблицы и содержимое объектов, на которые ссылаются акты. SHA-256 каждого объекта проверяется при чтении снимка и восстановлении. Полные JSON-версии 2.0, 3.0 и 4.0 остаются совместимыми: отсутствующее состояние фоновых заданий создаётся заново, старые поля объектов и ключи периодов нормализуются до проверки схемы. Тест сравнивает реестр бэкапа со схемой: добавление таблицы без включения в резервирование ломает gate. Снимок читается в REPEATABLE READ READ ONLY; запись файла атомарная, каталог имеет права 0700, файл — 0600.

Транзакционный restore сначала проверяет формат, строки и файлы, записывает проверенные неизменяемые объекты в постоянный каталог (это позволяет восстановить потерянный каталог), создаёт предвосстановительную копию, затем в одной транзакции блокирует таблицы и восстанавливает данные в порядке FK. Ошибка вставки откатывает все изменения. Восстановленные сессии отзываются. Неполный формат 1.0 автоматически восстанавливать запрещено: недостающие данные требуют отдельного восстановления из полного PostgreSQL dump.

Архивы содержат конфиденциальные данные. В production обязателен ACCESS_CODE_SECRET и отдельное защищённое хранение ключа. Новые архивы читаются и восстанавливаются потоком; большое восстановление выполняется `deploy/restore-backup.sh` в режиме обслуживания. Старые JSON-снимки ограничены 64 MiB.

Список счетов использует страницы по 100 записей (максимум API 200) и серверные поиск, сортировку и фильтры. Для интерфейса сохранены нумерованные страницы; для экспорта используется keyset-пагинация по UUID. HTTP-запрос без `page` возвращает первую ограниченную страницу и метаданные. OFFSET ограничен первыми 10000 совпадениями; UI показывает предел и предлагает уточнить фильтр. Полный экспорт остаётся доступен независимо от этого предела. Отчёт отдельного клиента ограничивает счета в SQL. Списки актов выбирают только метаданные: без base64 и внутренних ключей объектов.

## Архитектурные изменения из ревью

| Принцип | Изменение |
|---|---|
| SRP | `InvoiceDetailsDialog` сокращён до координатора из 293 строк; загрузка в `useInvoice`, редактирование в `useInvoiceCommands`, условия/оплата/расходы/расчёты — в отдельных компонентах `details/`. Финансовые команды, audit и outbox находятся на серверной границе приложения. |
| DRY | Один финансовый движок и механизм обновления проекции, общие DTO/валидация ответов, роли и схемы, централизованное обновление связанных React-запросов после редактирования. |
| OCP | `SCHEME_POLICIES` — исчерпывающий реестр финансовых схем. Таблицы ролевых проекций сервера и реестр возможностей UI типизированы через `Record<UserRole, …>`; новая роль требует явного определения политики. |
| ISP | `IStorage` заменён 7 предметными интерфейсами: SessionStore, InvoiceRepository, DirectoryStore, ReportingQueries, DocumentsRepository, RecurringRepository, AuditWriter. Каждый роут получает используемые операции через отдельный `Pick`. |
| DIP | Роутеры и middleware создаются фабриками. `server/routes.ts` связывает зависимости; DatabaseStorage, InvoiceCommands, BackupService и репозитории принимают БД/хранилище параметром. Auth-router получает LoginAttemptLimiter из composition root; сам лимитер не импортирует экземпляр БД. HTTP-тесты передают локальные заглушки без изменения singleton. |

График финансов загружается отдельным модулем. В проверенной production-сборке основной chunk около 220 kB, карточка счёта около 151 kB, самый большой chunk графиков около 361 kB; предупреждений о chunk >500 kB нет. Это размеры файлов до gzip, не измерение скорости на production.

## Документы и большие выгрузки

Специальные клиентские отчёты (предпросмотр, HTML, PDF, XLSX) читают счета страницами по 200 и ограничены 2000 счетами на запрос. Превышение возвращает 413 с предложением сузить период; частичный документ не выдаётся. Это ограничивает память форматов, которым нужна целая разметка. Общая административная XLSX-выгрузка остаётся потоковой и этого ограничения не имеет.

`ObjectStore` отделён от SQL. Текущий адаптер `FileObjectStore` хранит неизменяемые объекты на частном постоянном диске по SHA-256; каталог имеет права 0700, файлы — 0600. Он не требует внешнего аккаунта S3. `DOCUMENT_OBJECT_DIR` должен указывать за пределы web root и каталога приложения. Максимальный размер загружаемого файла — 10 MiB; ошибочный base64 и превышение размера возвращают 400. Имя объекта не принимается от пользователя.

`GET /api/acts/:id/content` сначала проверяет доступ к родительскому счёту и типу акта, затем открывает поток. Новые файлы не записываются в `signed_acts.file_data`. Старые base64 доступны до переноса командой `db:migrate:documents`: она обрабатывает по 1 строке с блокировкой, сначала сохраняет файл, затем обновляет SQL, допускает безопасный повтор. Объекты не удаляются вместе со строкой акта: это сохраняет доступность снимков. Очистку объектов следует связывать со сроком хранения всех бэкапов; автоматического GC нет.

Общая XLSX-выгрузка `/api/admin/export` читает счета и расходы порциями по 200 и использует streaming writer ExcelJS. Фильтры проверяются до отправки заголовков файла. Тест скачивает и открывает настоящий XLSX с 201 счётом из 2 порций. Справочник клиентов и его итоги занимают память пропорционально числу клиентов. Клиентские специальные отчёты ограничены scope клиента и 2000 счетами. Новые резервные копии используют потоковый `.fdb` с документами и проверкой целостности. PostgreSQL dump и каталог объектов дополнительно сохраняются перед каждым развёртыванием.

## Проверки перед выпуском

Требуются Node.js 26 и PostgreSQL 16. Команды:

```sh
npm ci
npm run check
TEST_POSTGRES_URL=postgres://postgres:postgres@127.0.0.1:5432/postgres npm run test:postgres
npm audit --audit-level=moderate
```

`test:postgres` создаёт уникальную временную БД, применяет миграции, проверяет гонки и удаляет только свою БД в finally. Боевой `DATABASE_URL` он не использует. В CI PostgreSQL создаётся отдельным service container.

Полный `npm audit` и production audit: **0 уязвимостей**. Цепочка Tailwind 3 → braces удалена обновлением до Tailwind 4; исключений advisory и `audit fix --force` нет. Overrides ExcelJS UUID и esbuild проверены сборкой, генератором миграций и XLSX-тестом с conditional formatting.

Клиент и сервер компилируются с `strict: true`. ESLint допускает **0 ошибок и 0 предупреждений**. Исправлены зависимости React hooks и разделены exports компонентов/контекстов для Fast Refresh. Tailwind 4 требует современных браузеров: Chrome/Edge 111+, Safari 16.4+, Firefox 128+. Стили переменных CSS и мобильная сетка проверены в браузере после обновления.

## Миграция существующей базы

1. Сделать полный `pg_dump` и проверить восстановление в отдельную PostgreSQL-БД.
2. Проверить дубликаты `invoice_calculations.invoice_id`: миграция 0002 останавливается при таких дубликатах. Исторические счета с одной парой `(recurring_invoice_id, issue_date)` сохраняются целиком. Миграция назначает неизменяемый уникальный `recurring_occurrence_key` самому раннему счёту каждого события; дополнительные исторические счета остаются с NULL. Генератор использует этот ключ, поэтому редактирование даты счёта не позволяет повторно сгенерировать тот же период. Денежные факты, статусы и связи старых счетов не меняются.
3. Если база ранее создавалась через `db:push` и в ней нет `drizzle.__drizzle_migrations`, сначала сопоставить её схему со снимком 0001 и оформить baseline журнала с реальными hash/timestamp миграций. Нельзя просто отметить старые миграции применёнными без этой сверки. Runner останавливается с явной ошибкой для существующей БД без журнала.
4. Прогнать миграции 0002–0005 и smoke-проверки на восстановленной копии. Проверить старые номера, суммы, роли, акты и формат бэкапа.
5. Создать постоянный каталог объектов, принадлежащий пользователю приложения (обычно `/var/finance-duck/objects`, права 0700), и задать `DOCUMENT_OBJECT_DIR` в `.env`. Сделать резервную копию каталога вместе с базой. После миграции 0003 выполнить `node --env-file=.env dist-server/migrateDocuments.js`; сверить число актов и выборочно скачать старые файлы. Повторный запуск возвращает `migrated: 0` для уже перенесённых строк.
6. В согласованном окне обслуживания применить `npm run db:migrate` с production-окружением и запустить новую сборку. В deployment-скрипте больше нет автоматического `db:push` и молчаливого пропуска миграции при отсутствии `.env`.

17.10.2026 исправления опубликованы в основной ветке `timeweb-migration` и развёрнуты на https://fin-dohod.ru/. Применены миграции 0002–0003 и перенос 15 документов. Полный протокол выпуска и проверки данных: [выпуск 17.10.2026](releases/2026-10-17.md). В первоначальный выпуск нагрузочные измерения не входили. Последующее измерение и ограничения приведены в [протоколе работы с объёмом данных](backup-and-capacity.md).

## Дополнение повторной проверки 17.10.2026

Первый выпуск не закрывал все сценарии: отсутствовали отдельный worker с сохранением состояния и очистка лимитера, replay не перепроверял доступ, recurring обходил audit/outbox и мог зависнуть на существующем периоде; совместимость старого полного бэкапа не учитывала новое поле ключа. Эти пробелы исправлены и воспроизведены регрессионными тестами. Дополнительно проверены скрытый счёт под видимым шаблоном, дата одного периода, перенесённая на другой период, и повтор удаления расхода.

`deploy/deploy.sh` требует чистый коммит, готовит отдельный каталог и атомарно переключает symlink. `activate-release.sh` сохраняет PostgreSQL dump и объекты перед миграцией, проверяет web и heartbeat worker с commit нового релиза, записанный после переключения (сбой одного шаблона периодики виден в результате задания и не откатывает релиз); при ошибке возвращает предыдущий код. Миграция 0004 только добавляет таблицу и индекс и совместима с предыдущим приложением. Для будущей несовместимой миграции нужен отдельный план восстановления БД: переключение symlink не откатывает SQL. Перед активацией обязательны PostgreSQL-регрессии и репетиция миграции на восстановленной копии.

## Завершение сверки списка, 17.10.2026

- Полная страница `InvoicePage` и диалог используют один `useInvoiceData`; типы InvoiceDto/ExpenseDto выведены из Zod-схем. Вознаграждение зависит от схемы; расходы читают `executorExpensesTotal` и `paidByAdmin`. Отсутствующая в ролевом ответе сумма не превращается в ноль. Ошибка загрузки расходов видна пользователю.
- Исправлены двойные `/api` у бухгалтера и 2 графиков планирования. У бухгалтерских документов и журнала есть состояния ошибки и повтора. Документы страницами, с поиском.
- Балансы клиентов, годовые итоги партнёра и ассистента, статусы актов и закрывающих документов агрегируются в SQL. Итоги охватывают все совпадения; клиентские группы и вложенные счета загружаются страницами. В сводке актов устранён отдельный запрос на каждый счёт. Суммы берутся из канонической проекции, включая нулевой остаток и переносы.
- Выбор счёта для оплаты и переноса использует общий InvoicePicker с серверным поиском. Выбранный счёт сохраняется при переходе на другую страницу. Нет скрытого ограничения выбора первой страницей.
- Второй Excel-маршрут `/api/my-invoices/export` тоже переведён на streaming WorkbookWriter, keyset-порции счетов/расходов и commit строк. Роль ограничивает выборку до формирования файла. `/api/financial-summary` больше не отдаёт неограниченный массив счетов.
- Серверный расчёт принимает FinancialInputs и возвращает канонические десятичные строки. Periodic и transfer overrides используют Decimal; numeric(15,2) проверяется после округления. Переполнение возвращает 400 с откатом команды. Числа в UI служат отображению, а не источником для сохранения проекции.
- Общий API-клиент поддерживает схему ответа. Для identity/invoicing введён реестр обязательных проверок, который срабатывает и без явно переданной схемы. Неверный ответ финансовой команды сохраняет ключ идемпотентности для повтора. Формы транспортных данных ассистента теперь camelCase и агрегированные; представления для UI могут использовать свои имена полей.
- Auth-router получает порт лимитера из composition root. Модуль лимитера не подключается к глобальной БД; фабрика получает конкретное соединение, в том числе изолированное в регрессиях.
- `deploy/restore-backup.sh` восстанавливает `.fdb` в новую пустую БД, сверяет число и SHA-256 отпечатки строк всех 22 таблиц, точные numeric-итоги и содержимое документов. После проверки останавливает сервисы, сохраняет текущий dump/объекты и одной SQL-транзакцией меняет имена БД. Проверяет запуск; при ошибке возвращает прежнюю БД. Прежняя БД и доказательства сохраняются. Restore и deploy используют общий maintenance lock.

Новые регрессии: HTTP-выборка 205 счетов, граница OFFSET, поиск последней записи, полные суммы при пагинации, роли/даты/нулевой остаток, диапазон денег, 5 ролей полной страницы, бухгалтерские вкладки и ошибки, scoped Excel. PostgreSQL-проверка включает shadow restore, изменение суммы на 1 копейку, сбой между переименованиями и обратное переключение. Финальный протокол проверки и выпуска: [завершение списка](releases/2026-10-17-review-completion.md).
