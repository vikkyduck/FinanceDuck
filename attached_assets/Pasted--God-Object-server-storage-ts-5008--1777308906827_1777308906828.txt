Для системы учета:
🔴 Критично: God Object в ядре системы
server/storage.ts — 5008 строк делает ВСЁ одновременно:
* Работу с БД (persistence)
* Финансовые расчёты (calculateInvoiceServer)
* Агрегацию дашборда (getAdminDashboardStats)
* Бизнес-логику доступа
server/routes.ts — 3073 строки смешивает:
* Транспортный слой (HTTP)
* Rate limiting с состоянием в памяти
* Маппинг прав доступа
* Оркестрацию бизнес-операций
Это нарушение SRP (Single Responsibility Principle) в чистом виде.

🔴 Критично: Дублирование финансовых формул
Одна и та же логика расчётов по схемам (partner_10, agency_30 и т.д.) живёт в двух местах:
* server/storage.ts → calculateInvoiceServer()
* src/lib/invoiceCalculations.ts → calculateInvoice()
Добавление новой схемы требует правок в обоих файлах. При расхождении версий — молчаливые финансовые ошибки. Это уже произошло — именно отсюда баги с netProfitAdmin vs clientBill.

🔴 Критично: Катастрофа производительности в дашборде
getAdminDashboardStats() загружает ВСЕ счета в память и агрегирует их циклом в JavaScript. При 1000+ счетах это приведёт к таймаутам. Всё это должно быть одним SQL-запросом с GROUP BY.

🟠 Серьёзно: Безопасность
* Rate limiting: хранится в Map в памяти — обнуляется при перезапуске, не работает в multi-instance
* IDOR-риск: фильтрация по роли на уровне полей недостаточна — row-level фильтрация должна быть в КАЖДОМ запросе к БД
* Отсутствие индексов: нет индексов на invoices(status, payment_date), invoices(partner_id), invoices(client_id) — основные пути всех дашбордов

🟡 Типобезопасность
Числовые поля БД везде хранятся как строки и конвертируются через parseFloat() — потенциальные ошибки округления в финансовых расчётах. Нет централизованной утилиты для работы с денежными суммами.
