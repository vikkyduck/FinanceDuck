# Завершение замечаний после выпуска 2a3ad07

Административный архив завершает сценарий сохранения счёта с платежами: кнопка в карточке и фильтры «Рабочие счета / Архив / Все, включая архив». Архивирование и возврат выполняет только admin, через транзакционную команду с блокировкой, идемпотентной квитанцией и аудитом. Статус, суммы, платежи, расходы, переносы, периоды и updated_at не меняются. Клиент, партнёр, ассистент и бухгалтер сохраняют прежние правила чтения. Архивная отметка доступна только администратору. Финансовые отчёты и выгрузки включают архивные счета; параметр archive применяется только явно, к административному списку. Счётчики и варианты фильтров относятся к выбранному разделу. После исчезновения последней строки страницы список возвращается на существующую страницу.

Миграция 0007 добавляет nullable archived_at. Существующие счета автоматически в архив не отправляются. Исторические значения 47 согласованных счетов не пересчитываются. Механизм консолидации остатков нескольких источников на один счёт сохраняется.

Новый FDB writer использует schema 6. Reader принимает schema 5 и 6; только для schema 5 отсутствующий archivedAt дополняется null. Аналогичная миграция предусмотрена для старого JSON. Повреждённый schema 6 с отсутствующим полем отклоняется. Старые предрелизные копии сохраняются: предыдущая версия приложения не умеет читать новый schema 6.

При повторной проверке найден пропуск инвалидации после изменения hideFromAssistant. Его воспроизводит React Query регрессия: до исправления список и сводки оставались валидными после успешного PATCH. Теперь редактор метаданных вызывает общий invalidateFinancialQueries. Архив и возврат используют тот же механизм.

useInvoiceCommands стал композиционным фасадом. Состояния и команды условий, статуса/дат, метаданных/видимости разделены на useInvoiceFinancialTerms, useInvoiceStatusCommands и useInvoiceMetadataCommands; расходы и ручные периоды уже находятся в самостоятельных хуках. Публичный интерфейс карточки сохранён. dashboardRepo стал фасадом над adminDashboardRepo, partnerDashboardRepo, partnerDebtRepo, clientBudgetRepo и clientOverviewRepo. При переносе сохранены тела функций, SQL и расчёты; отдельная сверка синтаксических токенов подтвердила эквивалентность всех перенесённых функций.

Регрессии полного приложения покрывают архивирование оплаченного периодического счёта с переносом и платежом, повтор/конфликт ключа, запрет для остальных 4 ролей, скрытый бухгалтерский счёт, неизменность финансового отчёта и всех финансовых таблиц, возврат из архива, сохранение отметки в FDB 6 и восстановление FDB 5/старого JSON. Остальные R1–R8 сохраняют существующие регрессии.

## Измерения и процедура проверки

scripts/benchmark.ts получил ограниченные по времени фазы, отдельный soak, выборки RSS/heap/очереди пула и EXPLAIN (ANALYZE, BUFFERS) реальных запросов. Тест использует новую синтетическую БД с уникальным именем, удаляет только её и может остановиться при ухудшении публичного health endpoint. Маршруты используют тестовую авторизацию: это измерение SQL и HTTP обработчиков на аппаратуре VDS, а не доказательство предельной мощности всей production цепочки.

scripts/production-read-probe.ts выполняет только GET через существующую авторизованную сессию, ограничивает длительность и частоту и прекращает прогон после 3 ошибок. Cookie и содержимое ответов не записываются. Для production используется полный действующий стек. Результат включает перцентиль времени ответа по маршрутам и минутам и память процесса. Такой прогон устанавливает наблюдаемую рабочую нагрузку; максимальный предел отказа и многосуточная устойчивость из него не следуют.

Перед переключением требуется полный check, CI PostgreSQL, восстановление защищённого production dump в изолированной БД, миграция без финансовых изменений и восстановление старого зашифрованного FDB новой версией. Сверка старой схемы добавляет archived_at:null только при отсутствии столбца; имеющиеся значения не маскируются. После переключения повторяются ролевые сценарии, отпечатки 17 бизнес-таблиц и объектов, сверка кодов доступа с предрелизной копией и проверка рабочего сайта. Конкретные результаты и SHA фиксируются в протоколе выпуска.
